# 사내톡 프로젝트 브레인스토밍

> 이 문서는 현재 저장소와 요구사항분석서 v2를 바탕으로 정리한 기획 아이디어다. 아래의 제안 항목은 구현 완료 기능이 아니며, 사용자 검증과 우선순위 결정이 필요한 후보이다.

## 1. 프로젝트 한 줄 정의

C#/.NET 기반의 Windows 사내 메신저로, 직원이 하나의 서버에 접속해 1:1 대화와 채팅방, 파일 공유를 사용하고 관리자는 계정과 운영 기록을 관리한다.

## 2. 해결하려는 문제 가설

실제 사용자 조사를 수행한 결과가 아니라 프로젝트의 사용 시나리오에서 도출한 가설이다.

- 직원이 서로 다른 메신저나 개인 연락 수단을 섞어 쓰면 업무 대화와 파일을 찾기 어렵다.
- 사내 계정 승인·퇴사자 접근 차단·감사 기록을 일반 소비자 메신저만으로 관리하기 어렵다.
- 큰 파일을 주고받는 동안 대화가 지연되거나, 연결이 끊긴 뒤 대화 흐름을 잃을 수 있다.
- 사내 서버와 데스크톱 환경에 맞는 운영·배포 방법이 필요하다.

## 3. 사용자와 기대 가치

| 사용자 | 현재 제공하는 가치 |
| --- | --- |
| 직원 | 계정으로 접속해 동료 찾기, 1:1·방 대화, 파일 공유, 지난 대화 확인 |
| 관리자 | 가입 승인, 계정 상태 관리, 비밀번호 초기화, 감사 기록과 통계 확인 |
| 서버 운영자 | 서버 실행·중지, TLS 및 DB 설정, 백업·로그·서비스 운영 |

## 4. 현재 구현 범위

현재 저장소 README와 요구사항 문서에 기재된 기능이다.

- 회원가입·로그인, 비밀번호 해시, TLS 통신, 선택적 LDAP 인증
- 1:1 메시지, 영구 채팅방, 멘션·답장·공감·수정·삭제·읽음·검색
- 친구·프로필·상태 표시와 오프라인 사용자에게 보내는 메시지
- 조각 단위 파일 전송과 전송 취소, 관리자 기능과 감사 로그
- Windows 서비스 감독, 테스트 프로젝트와 부하 테스트 도구

## 5. 개선 아이디어 보드

모든 제안은 사용자 요구와 운영 환경을 확인한 뒤 선택한다.

### A. 대화 검색을 더 쉽게

- **가설:** 메시지가 많아질수록 키워드 검색만으로 원하는 기록을 찾기 어렵다.
- **제안:** 기간, 방, 보낸 사람, 파일 포함 여부를 조합하는 검색 필터와 결과 내보내기를 검토한다.
- **검증:** 대표 사용자가 이전 대화에서 특정 파일이나 결정을 찾는 데 걸리는 시간과 성공률을 측정한다.
- **주의:** 검색 결과가 사용자의 방 참여·대화 열람 권한을 넘지 않도록 서버에서 권한을 다시 검사한다.

### B. 운영 점검을 반복 가능하게

- **가설:** DB 스키마 변경, 백업, TLS 인증서 교체는 운영자가 실수하기 쉬운 절차다.
- **제안:** 마이그레이션 사전 점검, 백업 복구 연습 절차, 인증서 만료 확인을 운영 가이드와 도구로 보강한다.
- **검증:** 빈 DB와 기존 DB 각각에서 설치·업데이트·복구 절차를 재현하고 소요 시간과 실패 지점을 기록한다.
- **주의:** 운영 DB에 자동으로 파괴적인 변경을 적용하지 않고, 백업·확인 단계를 둔다.

### C. 알림을 사용 상황에 맞게

- **가설:** 모든 방의 알림이 같은 방식이면 집중 업무 시간에 불편할 수 있다.
- **제안:** 방별 알림 수준, 조용한 시간, 멘션만 알림 같은 설정을 검토한다.
- **검증:** 직원이 알림을 끄는 빈도와 중요한 메시지를 놓치는 빈도를 비교한다.
- **주의:** 현재 상태 표시나 기존 방 알림 기능과 중복되는지 먼저 확인한다.

### D. 계정과 메시지의 관리 흐름 개선

- **가설:** 관리자는 가입·퇴사·감사 기록을 빠르게 확인해야 한다.
- **제안:** 계정 상태 변경 이력과 관리 작업을 한 화면에서 검색하고, 권한이 있는 범위에서 보고서를 내보내는 방안을 검토한다.
- **검증:** 운영자가 계정 관련 문의와 감사 요청을 처리하는 시간을 측정한다.
- **주의:** 개인 정보 최소화, 접근 권한, 보관 기간을 함께 설계한다.

### E. 데스크톱 사용성 다듬기

- **가설:** 로그인과 가입은 사용자가 처음 만나는 화면이라 오류 안내와 접근성이 중요하다.
- **제안:** 키보드만으로 화면을 완료할 수 있는지, 필드 오류가 구체적으로 안내되는지, 고해상도 배율에서 레이아웃이 유지되는지 점검한다.
- **검증:** 처음 사용하는 사람에게 회원가입·로그인을 부탁하고 막히는 지점과 완료 시간을 기록한다.
- **주의:** 화면 개선은 서버 인증 정책과 일치시킨다.

### F. 동시 접속 규모가 커질 때의 선택

- **가설:** 현재 세션별 전용 수신·송신 스레드 구조는 이해하기 쉽지만, 세션 수가 늘면 스레드 자원 부담이 증가한다.
- **제안:** 현재 부하 측정 결과와 실제 목표 동시 접속 수를 먼저 정한 뒤, 필요할 때 async I/O 구조와 데이터베이스 처리량을 비교한다.
- **검증:** 동일한 메시지 패턴에서 지연, CPU·메모리, 스레드 수, 유실·순서 오류를 비교한다.
- **주의:** 측정 없이 구조만 바꾸지 않는다. 단일 서버 부하 결과를 운영 용량으로 일반화하지 않는다.

## 6. 우선순위 제안

| 순서 | 후보 | 이유 |
| --- | --- | --- |
| 1 | 설치·마이그레이션·백업 복구 점검 | 데이터를 보호하고 시연·운영 재현성을 높임 |
| 2 | 로그인·가입 화면 사용성 및 키보드 접근성 점검 | 첫 사용자 흐름이며 개인 구현 경험과 연결하기 좋음 |
| 3 | 검색 필터와 알림 설정 조사 | 반복 사용 편의에 영향을 주지만 사용자 요구 검증이 필요함 |
| 4 | 부하 기준을 정한 뒤 비동기 I/O 비교 | 현재 구조의 한계를 측정으로 판단한 뒤 진행 |

## 7. 다음 단계

1. 잠재 사용자 3~5명에게 사내 대화·파일 공유에서 겪는 불편을 묻는다.
2. 불편 빈도와 해결 효과를 기준으로 후보 하나를 고른다.
3. 작은 시제품이나 화면 시안을 만들고 사용자가 실제로 해결하는지 확인한다.
4. 구현했다면 테스트 결과와 한계를 기록하고, 아직 구현하지 않은 아이디어와 구분한다.
