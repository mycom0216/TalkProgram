# AI 비서 설계와 평가 기록

사내톡에 **로컬 LLM + RAG**로 대화 기록에 질문하는 기능을 붙인 과정과, 측정한 결과(좋은 것과 나쁜 것 모두)를 적은 문서다.

## 1. 왜 이 주제인가

채용공고에서 C#/.NET 개발자 자리에 LLM·AI 경험을 함께 요구하는 흐름이 보였다. 확인한 공고 예시(잡코리아 검색 "C# LLM", 더팀스):

- C#/.NET 기반 시스템 개발자, C#·Java 개발자 정규직 (에스텍시스템, 젯스퍼트)
- ASP.NET Core 백엔드 + AI/ML 직무 (랭코드)
- .NET 프레임워크와 C#으로 자체 도메인 특화 LLM과 연계한 솔루션을 만드는 벤처 (더팀스 공고)
- 채용 분석 글에서 RAG, 벡터 DB, 임베딩, 청킹 경험을 자산으로 꼽음

그래서 **이미 C#으로 만든 사내 메신저**(TCP 서버, TLS, MariaDB, 관리자·감사 기능)에 AI 기능을 붙이면 "C#/.NET 백엔드 + RAG"를 한 프로젝트로 보여 줄 수 있다고 판단했다.
사내 메신저 대화는 외부 반출이 어려운 데이터라 **로컬 LLM**을 쓰는 이유가 분명하다.

> 시장 조사의 한계: 사람인은 목록이 자바스크립트로 그려져 내용을 읽지 못했고, 고용24는 확인하지 못했다. 위 목록은 잡코리아 검색 결과 일부와 공개 채용 페이지 몇 건이라 시장 전체를 대표하지 않는다. 지원할 회사의 공고를 직접 읽고 우대사항에 맞춰 이 문서의 강조점을 바꾸는 것을 권한다.

## 2. 구조

```
ChatApp.Rag        청킹 · BM25 · 벡터 · RRF · 권한 필터 · 답변/검증 · 임베딩 캐시 · Ollama 클라이언트 (외부 NuGet 없음)
ChatApp.Rag.Eval   질문 세트로 검색·답변 품질과 권한 누출을 측정하는 콘솔 도구
ChatApp.Server     AiAssistantService (패킷 처리, 색인 갱신, 대기열·간격 제한), MessageRepository.LoadForIndex
ChatApp.Client     AiAskForm (질문, 답, 근거 대화 표시)
ChatApp.Common     AiAskReq / AiAskRes 패킷과 모델
ChatApp.Tests      RagTests (39개: 청킹, 토큰, 검색, 권한, 캐시, 답변, 서비스 종단)
```

주요 설계 결정:

| 결정 | 이유 |
| --- | --- |
| 권한 필터를 순위 계산 **전**에 적용 | 검색 후에 거르면 점수·결과 개수·프롬프트에 남의 대화가 영향을 줄 수 있다. 대화 키(`room:번호`, `dm:사번|사번`)의 허용 집합 밖은 후보에도 안 들어온다. 키 모양이 이상하면 아무에게도 허용하지 않는다(fail closed) |
| 한국어를 **글자 bigram**으로 BM25 | 형태소 분석기 없이 조사 변화("배포는/배포를")에 대응. 의존성이 없고 CPU에서 1ms |
| BM25 + 벡터를 **RRF**로 합침 | 두 점수는 단위가 달라 더할 수 없다. 순위만 쓰는 RRF는 점수 보정이 필요 없다 |
| 임베딩을 **내용 해시로 캐시** | CPU 임베딩은 느리다. 대화가 늘어도 새 청크만 계산한다. 캐시 파일이 깨져도 비우고 다시 만든다 |
| **CPU 전용**(`num_gpu = 0`) | 이 PC의 GTX 1050(VRAM 2GB)에서 Ollama가 CUDA 오류로 죽는 것을 직접 겪었다. 저사양에서 이득도 거의 없다 |
| 질문을 **한 번에 하나씩**(SemaphoreSlim), 사람당 간격·대기열 제한 | CPU 추론을 동시에 돌리면 모두 느려진다. 수신 스레드는 붙잡지 않아 하트비트가 끊기지 않는다 |
| 근거 없으면 **LLM을 안 부름**, 인용 번호 검증 | 시간 절약과 환각 방지. 모델이 지어낸 출처 번호([9])는 버린다 |
| 기본 **꺼짐** | 대화를 색인하는 기능이라 관리자가 일부러 켜야 한다(secure by default) |

## 3. 측정 결과

환경: Ryzen 7 3700X, RAM 16GB, GPU 미사용(CPU만), embeddinggemma(임베딩) + kanana2:3b Q4(답변).
데이터: 가상 대화 32줄(방 3개 + 못 보는 인사 방), 질문 27개(답 있음 20, 답 없음 4, 못 보는 방 3). 실제 사내 데이터가 아니다.

### 3.1 검색

| 청크 최대 길이 | 청크 수 | Recall@1 (BM25 / 벡터 / 하이브리드) | Recall@3 |
| --- | --- | --- | --- |
| 300자 | 11 | 100% / 100% / 100% | 모두 100% |
| 120자 | 14 | 95% / 100% / 95% | 모두 100% |
| 60자 | 29 | 85% / 90% / 90% | 모두 100% |

해석: 데이터가 너무 작아 **방법 간 차이를 주장할 수 없다.** 하이브리드가 BM25보다 낫다고 말할 근거가 되지 못한다(60자 조건에서 벡터와 같은 수준). 실제 대화가 수천 건 이상일 때 다시 측정해야 한다.
검색 시간은 BM25 1ms, 벡터·하이브리드 약 36ms(질문 임베딩 포함).

### 3.2 권한

- 못 보는 방(`room:hr`)에 대한 질문 3개 × 3가지 검색 방법: **결과에 섞인 청크 0건**
- 대조군: 같은 질문을 "모든 방 허용"으로 검색하면 정답이 3위 안에 나옴(3/3). 검색이 비어서 통과한 것이 아님을 보인다.
- 단위 테스트: 제3자는 남의 1:1과 못 보는 방을 볼 수 없다. 프롬프트와 출처에 비밀 내용(`5.2`)이 없음을 확인한다.

### 3.3 답변 (여기가 약점)

첫 측정(검증 단계 없음)에서 3B 모델이 **근거가 없어도 그럴듯한 답을 지어냈다.** 예: 못 보는 방의 연봉 질문에 근거 없이 "3.5%"라고 답했다(실제 값과 무관한 환각이라 유출은 아니지만 틀린 답이다).
코사인 유사도로 거르려 했지만 답 있는 질문의 1등 코사인(최소 0.33)과 답 없는 질문(최대 0.50)이 겹쳐 **하나의 기준값으로는 가를 수 없었다.**

그래서 답을 만들기 전에 "근거에 답이 있는가"를 LLM에게 먼저 묻는 검증 단계를 넣었다.

| 시도 | 답 있는 질문 정답 | 거절(놓침) | 답 없는 질문 올바른 거절 | 지어낸 답 | 질문당 시간 |
| --- | --- | --- | --- | --- | --- |
| 검증 없음 | 16~17/20 | 0 | 4/7 | 3 | 2.4~2.7초 |
| 검증 v1 ("예/아니오 한 단어") | **4/20** | **15** | 6/7 | 1 | 2.0초 |
| 검증 v2 (형식 고정 + 예시) | 16/20 | 0 | 5/7 | 2 | 3.7초 |

- **v1은 실패**였다. 원인을 모델의 원래 응답으로 확인해 보니 "예" 대신 질문의 답("232")을 그대로 말해서 내가 거절로 해석한 것이었다(작은 모델의 형식 지시 이행 문제). 형식을 `판정: 예/아니오`로 고정하고 예시 3개를 붙여 v2로 고쳤다.
- v2의 이득은 **거절 4/7 → 5/7, 지어낸 답 3 → 2** 로 질문 1개 차이다. 표본이 작아 개선이라고 단정할 수 없고, 비용은 질문당 약 1.3초다. 안전 쪽(의심스러우면 거절)으로 기울어 기본값은 켬으로 두었다.
- 남은 오답은 검색이 맞아도 **모델이 엉뚱한 줄을 인용**하는 경우("500명 테스트는 언제?"에 메모리 수치 줄을 그대로 출력)와, 답 없는 질문에 "아직 정해지지 않았습니다"를 말하는 경우다.

### 3.4 다음에 해 볼 것

1. 근거 개수(TopK)를 4에서 2로 줄여 엉뚱한 줄 인용이 줄어드는지 측정
2. 더 큰 모델(7~8B)과 3B의 정확도·시간 비교 (이 PC는 RAM 16GB라 7B Q4까지 가능)
3. 질문 세트를 100개 이상으로 늘리고, 실제 대화 형태(오타, 줄임말, 긴 스레드)를 넣기
4. 방 대화에 "입장 시각 이후만" 규칙 적용, AI 질문의 감사 로그 기록(질문 본문은 남기지 않고 횟수만)

## 4. 면접 예상 질문

- **남의 비공개 대화가 답에 섞이지 않나요?** → 순위 계산 전에 권한 필터를 적용하고, 못 보는 방을 묻는 질문으로 누출 0건과 대조군(권한을 주면 나옴)을 함께 확인했다. 모양이 이상한 대화 키는 모두에게 막는다.
- **왜 클라우드 API가 아니라 로컬 LLM인가요?** → 사내 대화는 반출이 어렵다. 대신 3B 모델은 틀릴 수 있어, 근거 인용·거절·검증 단계·"근거 대화를 확인하세요" 안내로 보완하고 한계를 숫자로 적었다.
- **GPU 없이 어떻게 돌렸나요?** → CPU 전용. 구형 GPU가 CUDA 오류로 Ollama를 죽이는 것을 겪어 `num_gpu = 0`으로 고정했고, 임베딩 캐시와 직렬 처리, 간격·대기열 제한으로 서버를 보호했다. 질문당 약 2~4초.
- **개선이 실패한 적은?** → 검증 단계 v1이 정답 17개를 4개로 떨어뜨렸다. 모델 원문 응답을 확인해 원인(형식 불이행)을 찾고 v2로 고쳤다. 개선 폭이 작다는 것도 그대로 적었다.
- **한계는?** → 데이터 규모(가상 32줄), 3B 모델의 오답, 방 대화 입장 시각 규칙 미적용, 색인 갱신 지연(최대 10분), 첨부 파일 내용 미색인.

## 5. 직접 해 보기

```bash
ollama pull embeddinggemma
dotnet test ChatApp.Tests --filter "FullyQualifiedName~RagTests"          # Ollama 없이 (가짜 모델)
dotnet run --project ChatApp.Rag.Eval -c Release                          # 검색 품질 + 권한 (Ollama 필요)
dotnet run --project ChatApp.Rag.Eval -c Release -- --answers             # 답변 평가 (질문마다 LLM 호출, 몇 분)
```
